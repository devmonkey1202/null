# 01. Current State Audit

이 문서는 2026-05-21 시점의 v1 실제 상태를 고정합니다.  
문서 설명이 아니라 코드/빌드/테스트/실행 기준입니다.

## 1. 현재 프로젝트의 성격

현재 NULL은 아래 세 가지가 섞여 있습니다.

1. 디자인 에디터
2. 퍼블릭 런타임/배포 시스템
3. 범위가 넓은 서비스형 백엔드 실험장

문제는 이 세 가지가 강한 계약 없이 한 레포에서 뒤엉켜 있다는 점입니다.

- `src`: 439

Prisma 모델 수:

## 3. 코드 구조상 큰 문제

### 3.1 거대한 단일 파일

- `src/advanced/ui/AdvancedEditorView.tsx`: 22,970줄
- `src/advanced/runtime/player.tsx`: 10,461줄
- `src/components/messenger-demo-app.tsx`: 974줄
- `src/app/api/messenger/[...path]/route.ts`: 861줄

이 구조는 다음 문제를 만듭니다.

- 변경 영향 범위 파악이 어려움
- 사이드 이펙트 증가
- 테스트 단위 분리가 약함
- 상태/이벤트/렌더링 결합도 증가
- 회귀 위험 증가

### 3.2 런타임이 명시적 엔진이 아니라 특수처리 집합

`src/advanced/runtime/player.tsx`는 범용 앱 런타임이라기보다 다음 성격이 강합니다.

- 패턴 매칭 기반 UI 추론
- 페이지 이름/텍스트 이름 기반 맥락 추론
- 도메인별 특수처리 누적
- 메신저/알림/피드/노트/칸반/캘린더/빌링 등 다수 기능을 한 파일에서 해석

예시:

- `NATIVE_MESSENGER_PAGE_IDS` 하드코딩
- `matchesPattern`, `hasAncestorMatching` 기반 동작 분기

이 구조는 자유도를 높인 것이 아니라, 사실상 “암묵적 런타임 규칙”을 늘린 것입니다.

## 4. 에디터 실제 상태

### 4.1 우측 사이드바 클릭/편집 불가 원인 확인

직접 확인된 1차 원인:

- `showOnboarding`가 true일 때 전체 화면 오버레이가 클릭을 가로챔
- 파일: `src/advanced/ui/AdvancedEditorView.tsx`
- 핵심 상태: `showOnboarding`
- 핵심 오버레이: `fixed inset-0 z-[9999]`

결론:

- “사이드바 전체 로직이 완전히 죽었다”라기보다
- “온보딩 레이어가 입력을 막는 구간이 실제로 존재한다”

### 4.2 테스트와 실사용의 차이

일부 E2E는 실제 사용자의 편집 플로우를 그대로 검증하지 않습니다.

대표 예:

- `e2e/asset-library.spec.ts`는 `window.__ADVANCED_EDITOR__` 브리지를 사용
- 프리셋 삽입을 실제 사용 UI 조작이 아니라 테스트 브리지로 처리

의미:

- 테스트 통과 = 사용자 체감 편집 안정성 보장 아님

### 4.3 에디터 품질 판단

현재 에디터는 아래 단계에 가깝습니다.

- “고급 프로토타입 에디터”: 일부 가능
- “Figma 핵심 경험 재현”: 미달
- “복잡한 앱을 안정적으로 만드는 편집기”: 미달

## 5. 퍼블릭 런타임 실제 상태

### 5.1 퍼블릭 페이지 멈춤

`/p/...` 페이지의 1분 전후 멈춤 현상은 실제로 재현되었고, 일부 원인은 확인/완화했습니다.

조사한 원인:

- `standalone` 런타임에서 불필요한 타이머/리렌더
- 메신저 관련 폴링/상태 갱신 과다

완화 작업 흔적:

- `src/components/work-view.tsx`
- `src/advanced/runtime/player.tsx`

주의:

- 이 완화는 현재 로컬 미커밋 상태입니다.
- v2 설계와 별개의 임시 안정화 흔적입니다.

### 5.2 런타임 품질 판단

현재 런타임은 다음 단계에 가깝습니다.

- 단순 프로토타입/일부 앱 데모: 가능
- 고자유도 앱 런타임: 불안정
- 특수처리 누적 없이 일반화된 서비스 런타임: 아님

## 6. 메신저 관련 실제 상태

### 6.1 `/messenger`의 정체

`/messenger`는 에디터 산출물 기반 메신저가 아닙니다.

- `src/app/messenger/page.tsx`
- `src/components/messenger-demo-app.tsx`

즉, 별도 React 앱입니다.

### 6.2 메신저 백엔드

메신저용 API는 있습니다.

- `src/app/api/messenger/[...path]/route.ts`

이 라우트 안에 다음이 섞여 있습니다.

- 회원가입/로그인
- 친구 요청/수락
- 대화방
- 메시지
- 알림
- 통화

문제:

- 기능 범위 대비 테스트/도메인 분리가 약함
- 실제 프로덕트 엔진이 아니라 데모 성격이 강함

### 6.3 메신저 UI 상태

`src/components/messenger-demo-app.tsx`는 다음 문제를 안고 있습니다.

- 폴링 기반 갱신
- 기능이 한 파일에 집중
- 프로덕트 내부 계정 모델과 플랫폼 계정 모델이 분리돼 보이지 않음
- “에디터에서 만든 앱”이 아니라 “별도 데모 앱”이라는 성격이 강함

결론:

- 메신저는 “플랫폼이 지원하는 대표 앱”이 아니라
- “플랫폼 바깥 데모와 플랫폼 안 특수처리의 혼합물”입니다.

## 7. 백엔드/DB 실제 상태

### 7.1 Prisma / 타입

직접 확인:

- `npm run verify:prisma`: 통과
- `npm run verify:types`: 통과

의미:

- 스키마 문법과 타입 수준은 현재 일단 맞습니다.
- 이것만으로 제품 신뢰성을 보장하지는 않습니다.

### 7.2 Build

직접 확인:

- `npm run build`: 실패

실패 이유:

- 프로덕션 환경에서 `IP_HASH_SALT` 필수
- `src/lib/request.ts`에서 production + empty salt면 즉시 throw
- 현재 `.env.production.local`에는 `IP_HASH_SALT=""`

즉:

- 로컬 개발 빌드 재현성은 현재 깨져 있습니다.
- 프로덕션 환경 변수 관리가 불완전합니다.

### 7.3 로컬 스택

`.env` 기준 로컬 DB:

- `DATABASE_URL=postgresql://postgres:postgres@localhost:15432/null_db?schema=public`

`docker-compose.yml` 기준 기대 인프라:

- Postgres: `15432`
- Redis: `6379`

직접 확인:

- 현재 `localhost:15432` 닫혀 있었음
- `docker compose up -d db redis` 실패
- 이유: 현재 머신에서 Docker engine 미가동

즉:

- 로컬 풀스택 개발 전제부터 항상 보장되는 상태가 아닙니다.

## 8. 테스트 실제 상태

### 8.1 유닛 테스트

직접 확인:

- `npm run verify:unit`
- 결과: 125개 파일, 536개 테스트 통과

이건 좋은 신호입니다.  
하지만 다음 한계가 있습니다.

- 상당수는 mock 기반
- 실제 DB/실제 실시간/실제 편집 흐름을 전부 검증하지 않음
- JS DOM 환경 한계 경고 존재

예:

- `tests/app-auth-session.test.ts`는 `@/lib/db` mock
- `tests/service-realtime.test.ts`는 `@/lib/db` mock

### 8.2 E2E 테스트

장점:

- API/페이지 기본 smoke는 있음
- publish/live/replay 같은 기본 경로 검증 있음

한계:

- 편집기 핵심 UX를 실제 사용자 조작 기준으로 깊게 보장하지 않음
- 메신저/앱 빌더 전체 시나리오 E2E가 없음
